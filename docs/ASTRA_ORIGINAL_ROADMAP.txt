============================================================
로컬 문서 디자인 / PDF 리디자인 앱 개발 로드맵
문서 버전: 1.0
============================================================

[0. 이 문서의 목적]

이 문서는 다른 AI 또는 개발자가 프로젝트 배경을 모르는 상태에서도
전체 목표와 단계별 범위를 이해하고,
해당 단계의 상세 구현 프롬프트를 작성할 수 있도록 만든 인수인계 문서다.

단계별 설명은 구현 범위와 완료 기준이다.
실제 구현 여부는 맨 아래 "진행 기록" 및 프로젝트 코드를 확인해야 한다.

중요:
- 문서에 기능이 적혀 있다고 구현 완료된 것으로 간주하지 않는다.
- 현재 단계보다 뒤에 있는 기능을 미리 구현하지 않는다.
- 필요한 기반 구조는 만들되 미래 기능 때문에 과도하게 설계하지 않는다.
- 각 단계가 실제로 사용 가능한 상태가 된 후 다음 단계로 넘어간다.


============================================================
[1. 프로젝트 배경과 최종 목표]
============================================================

1-1. 최초 사용 목적

사용자는 국비학원 사이트에 제출하는 회고록을 작성한다.
늘 비슷한 양식 대신, 여러 디자인을 선택해서
보기 좋은 회고록 PDF를 만들고 싶어 한다.

첫 버전은 사용자가 글을 직접 입력하거나 붙여넣고,
디자인을 선택한 다음 PDF로 저장하는 도구다.

학원 사이트 업로드는 사용자가 직접 한다.
사이트 자동 로그인이나 자동 제출은 프로젝트 범위가 아니다.

학원 사이트가 PDF 첨부를 받는지는 별도 확인이 필요하다.
PDF 첨부가 불가능한 경우 다른 출력 형식은 추후 별도로 판단한다.

1-2. 최종 목표

최종적으로 다음 흐름을 제공하는 로컬 앱을 만든다.

기존 PDF 업로드
→ 텍스트·이미지·표·문서 구조 추출
→ 사용자가 추출 결과 확인 및 수정
→ 내장 디자인 또는 외부 레퍼런스 선택
→ 새로운 레이아웃으로 재구성
→ 미리보기와 오류 확인
→ 새로운 PDF 저장

레퍼런스는 다음 방식으로 확보한다.
- 내장 테마
- 사용자가 넣은 이미지 또는 PDF
- 지원되는 URL
- 인터넷 검색 연동

1-3. 핵심 제품 방향

원본 PDF의 모든 요소를 제자리에서 직접 수정하는 편집기가 아니다.

기본 방향은:
"원본 문서의 내용을 구조화한 후,
새로운 디자인으로 재조판하는 도구"다.

원본과 페이지 수, 줄바꿈, 위치가 달라질 수 있다.

"모든 PDF를 완벽하게 자동 변환"한다고 약속하지 않는다.
지원 가능한 문서 범위를 정하고,
자동 처리에 실패한 부분은 사용자가 수정할 수 있게 한다.

1-4. 개발 및 판매 방향

우선 사용자가 본인 문서에 실제로 사용한다.
이후 안정화하고 필요하다면 상품화한다.

7단계까지 모두 완성해야만 판매할 수 있는 것은 아니다.
좁은 기능이라도 안정적이면 판매 가능성을 검토할 수 있다.

가능한 판매 형태:
- 도구로 제작한 문서 디자인 결과물 납품
- 특정 고객용 문서 제작 도구 구축
- 프로그램 자체 판매

판매 가능성은 기능 수가 아니라
결과물 품질, 신뢰성, 고객 수요로 판단한다.


============================================================
[2. 모든 단계에 적용되는 원칙]
============================================================

2-1. 내용과 디자인 분리

문서 내용과 디자인 설정은 별도로 저장한다.
테마를 바꿔도 원문이 바뀌면 안 된다.

2-2. 내용 보존 우선

디자인 변경 과정에서 문장, 숫자, 표 데이터를
임의로 요약·교정·삭제·재작성하지 않는다.

추후 AI를 사용하더라도 스타일 분석과 내용 수정을 구분한다.

2-3. 공통 문서 렌더러

미리보기와 PDF 출력은 가능한 한
동일한 문서 컴포넌트와 스타일 규칙을 사용한다.

화면과 PDF 결과가 완전히 동일하다고 가정하지 않는다.
실제 인쇄 결과를 별도로 검증한다.

2-4. 단계적 데이터 확장

저장 데이터에 schemaVersion을 둔다.
구조가 바뀌면 이전 문서를 읽는 마이그레이션을 고려한다.

초기부터 거대한 범용 문서 모델을 만들 필요는 없다.
단계에 맞춰 확장한다.

2-5. 로컬 우선

문서 편집과 저장은 기본적으로 로컬에서 수행한다.

외부 AI나 검색 API는 필요한 단계에서 선택적으로 도입한다.
외부로 전송하는 데이터, 목적, 비용을 명확히 표시한다.

로컬 앱이라고 모든 기능이 자동으로 오프라인인 것은 아니다.

2-6. 개인정보와 안전

사용자 문서 내용을 임의로 외부 전송하거나 로그에 남기지 않는다.
외부 HTML이나 문서 내용을 그대로 실행하지 않는다.
API 키를 프론트엔드 코드나 저장소에 포함하지 않는다.

2-7. 라이선스 확인

폰트, 이미지, 템플릿, 라이브러리의 이용 조건을 기록한다.
개인 사용 가능 여부와 재배포·상업 판매 가능 여부는 구분한다.

예:
PyMuPDF를 채택할 경우 AGPL/상용 라이선스 조건을 검토한다.

2-8. 검증 가능한 보고

실제로 실행한 테스트만 성공했다고 보고한다.
확인하지 못한 항목은 미확인 또는 수동 테스트 필요로 표시한다.


============================================================
[3. STEP 1 — 학원 제출용 회고록 꾸미기]
============================================================

목적:
사용자가 작성한 회고록을 세 가지 디자인 중 하나로 꾸며
학원에 제출할 PDF를 만든다.

사용 흐름:
회고록 입력
→ 테마 선택
→ 색상·폰트·본문 크기 조절
→ 미리보기
→ 브라우저 인쇄에서 PDF 저장

입력 항목:
- 제목
- 작성자: 선택 입력
- 작성일: 로컬 기준 오늘을 기본값으로 사용
- 오늘 배운 내용
- 어려웠던 점
- 해결 과정
- 느낀 점 및 다음 계획

필수 기능:
- 입력 내용 실시간 미리보기
- 여러 줄과 문단 구분 보존
- 빈 본문 섹션은 섹션 제목까지 숨김
- 작성자 미입력 시 작성자 영역 숨김
- 예시 회고록 불러오기
- 초기화
- 테마 변경 시 내용 유지

테마:
1. 깔끔한 보고서
2. 미니멀 노트
3. 학습 다이어리

테마는 색상만 다르게 하지 않는다.
제목 배치, 구분선, 섹션 라벨, 여백도 구분한다.

디자인 설정:
- 테마 3개
- 포인트 색상 팔레트 6개
- 본문 크기: 작게 / 보통 / 크게
- 폰트: 고딕 / 명조

폰트:
외부 다운로드 없이 시스템 폰트를 사용한다.
OS에 따라 실제 폰트가 다를 수 있음을 안내한다.

화면:
- 데스크톱: 왼쪽 입력·설정, 오른쪽 미리보기
- 작은 화면: 세로 배치
- 한국어 UI
- 문서 미리보기는 A4 폭을 기준으로 표시

PDF 출력:
- window.print() 사용
- @page로 A4 크기와 여백 설정
- 앱 UI는 인쇄에서 제외
- 문서만 인쇄
- 긴 내용은 여러 페이지로 이어짐
- 정확한 페이지별 미리보기 엔진은 만들지 않음
- 최종 페이지 나눔은 브라우저 인쇄 미리보기에서 확인

주의:
- 한 페이지보다 긴 섹션이 잘리지 않게 한다.
- 긴 섹션 전체를 무조건 break-inside: avoid로 묶지 않는다.
- 긴 URL과 공백 없는 문자열의 넘침을 방지한다.
- 배경 그래픽이 꺼져도 본문을 읽을 수 있게 한다.
- 브라우저 머리글·바닥글 해제 방법을 안내한다.
- Chrome / Edge를 우선 지원한다.

저장:
- localStorage에 현재 문서와 디자인 자동 저장
- schemaVersion: 1 포함
- 새로고침 시 복원
- 잘못된 저장 데이터로 앱이 죽지 않게 처리
- 저장 실패 시 경고하되 편집은 유지
- 초기화 시 저장 데이터도 함께 초기화
- 예시 불러오기와 초기화는 기존 내용이 있으면 확인

권장 기술:
- React
- TypeScript
- Vite
- 일반 CSS 또는 CSS Modules
- 백엔드 없음
- 데이터베이스 없음
- 외부 API 없음
- CDN 없음
- 개발 서버는 localhost에만 바인딩

최소 코드 분리:
- 회고록 데이터 타입 및 초기값
- 테마와 디자인 설정
- 입력 폼
- 디자인 설정 패널
- 공통 문서 렌더러
- 로컬 저장 처리
- 화면 및 인쇄 CSS

제외:
- 기존 PDF 업로드
- 이미지 업로드
- OCR
- AI
- 인터넷 검색
- 표 편집
- 드래그 편집
- 여러 문서 관리
- 로그인·결제
- 설치형 앱 패키징

완료 기준:
- 개발 서버 실행과 프로덕션 빌드 성공
- 실제 회고록 입력 및 테마 변경 가능
- PDF에 앱 UI가 나오지 않음
- 한글이 정상 출력되고 텍스트 선택 가능
- 여러 페이지 분량이 누락 없이 출력
- 새로고침 복원과 초기화 정상 동작
- 사용자가 실제 회고록 하나를 PDF로 만들어 확인

학원 제출까지 해보면 가장 좋은 실제 검증이 된다.


============================================================
[4. STEP 2 — 개인 문서 제작기]
============================================================

목적:
회고록 고정 양식을 넘어
학습일지·간단한 보고서 등도 작성할 수 있게 한다.

사용 흐름:
새 문서 또는 저장 문서 선택
→ 섹션 편집
→ 이미지 추가
→ 디자인 선택
→ 저장 및 PDF 출력

추가 기능:
- 섹션 추가·삭제·제목 수정
- 섹션 순서 변경
- 이미지 업로드
- 이미지 설명 및 정렬·크기 조절
- 여러 문서 저장·불러오기
- 문서 이름 변경 및 복제
- 프로젝트 파일 내보내기·가져오기
- 검증된 테마 추가

구현 방향:
- 문서를 순서 있는 블록 구조로 확장
- 최소 블록 종류: 제목, 문단, 이미지
- 순서 변경은 위/아래 버튼만으로도 충분
- 자유로운 캔버스 편집기는 만들지 않음
- 이미지와 여러 문서는 IndexedDB 등 적합한 저장소 사용
- 이미지를 localStorage에 무제한 저장하지 않음
- 내보낸 프로젝트는 다른 환경에서도 이미지 복원 가능해야 함
- STEP 1 저장 데이터를 읽는 변환 처리 제공

제외:
- PDF 분석
- AI 스타일 분석
- 인터넷 검색
- 실시간 협업
- 복잡한 표 편집

완료 기준:
- 이미지 포함 문서 생성 가능
- 저장 후 다시 열었을 때 내용·이미지·디자인 유지
- 프로젝트 내보내기 후 가져오기로 복원 가능
- 순서 변경과 삭제가 정상 동작
- 이미지가 PDF에서 잘리거나 과도하게 늘어나지 않음


============================================================
[5. STEP 3 — 기존 PDF 가져오기]
============================================================

목적:
기존 PDF에서 내용을 추출하여
앱의 문서 구조로 변환하고 새 디자인을 적용한다.

지원 대상:
우선 텍스트가 선택 가능한 단순한 PDF.
텍스트 위주의 단일 열 보고서부터 지원한다.

사용 흐름:
PDF 선택
→ 내용 추출
→ 추출 결과 확인
→ 제목·본문·순서 수정
→ 테마 적용
→ PDF 출력

추가 기능:
- PDF 텍스트와 위치 정보 추출
- 가능한 범위에서 이미지 추출
- 제목·본문·캡션의 기본 분류
- 읽기 순서 추정
- 원본 PDF와 추출 결과 비교
- 블록 종류 및 순서 수동 수정
- 지원하지 못한 요소에 대한 경고

구현 방향:
- 기존 편집기와 문서 렌더러 재사용
- PDF 추출기를 별도 모듈로 분리
- 블록에 원본 페이지·좌표 등 출처 정보를 보관
- 단순 문자열 추출과 읽기 순서 복원은 별개로 취급
- 머리글·바닥글 제거는 원문을 확인할 수 있게 처리
- 불확실한 내용은 조용히 삭제하지 않음

기술 선택:
브라우저 기반 추출로 충분한지 먼저 검토한다.
필요하면 Python 로컬 서비스를 추가한다.

도구 선택은 다음을 비교한 후 확정한다.
- 한글 처리
- 이미지 추출
- 배포 난이도
- 성능
- 라이선스

제외:
- 스캔 PDF OCR
- 복잡한 표의 완벽한 복원
- 복잡한 다단 레이아웃의 완벽한 처리
- 원본과 동일한 페이지 수·배치 보장
- PDF의 모든 그래픽 요소 직접 편집

완료 기준:
- 사용자가 자주 쓰는 단순 PDF 5~10개로 테스트
- 추출 내용과 원본을 비교할 수 있음
- 오인식과 순서 오류를 사용자가 수정 가능
- 수정한 내용으로 테마 적용 및 출력 가능
- 추출이 부족한 문서를 성공한 것처럼 표시하지 않음


============================================================
[6. STEP 4 — 디자인 조합 엔진]
============================================================

목적:
소수의 고정 테마를 넘어
검증된 디자인 요소를 조합하여 여러 스타일을 제공한다.

사용 흐름:
문서 열기
→ 디자인 후보 탐색
→ 비교
→ 상세 조절
→ 즐겨찾기
→ 출력

추가 기능:
- 레이아웃 프리셋
- 폰트 조합
- 색상 팔레트
- 여백과 정보 밀도
- 제목·섹션 장식
- 이미지 배치 프리셋
- 여러 스타일의 비교 미리보기
- 사용자 스타일 저장 및 재사용

구현 방향:
- 디자인 토큰과 레이아웃 프리셋 분리
- 색상, 간격, 글자 크기 등을 토큰화
- 무작위 조합보다 검증된 조합 우선
- 어울리지 않거나 깨지는 조합은 제한
- 지원되는 스타일 설정을 명확한 스키마로 정의
- 이후 AI 스타일 분석은 이 스키마를 출력하도록 연결

성능:
수백 개 조합을 모두 전체 문서로 동시에 렌더링하지 않는다.
대표 페이지, 지연 로딩, 일부 후보 미리보기 등을 사용한다.

제외:
- 인터넷 검색
- AI 레퍼런스 분석
- 완전 자유 배치 편집기

완료 기준:
- 동일 문서에 여러 스타일 적용 가능
- 스타일 변경으로 내용이 바뀌지 않음
- 허용된 조합을 대상으로 잘림·겹침 테스트
- 스타일 저장 및 재사용 가능
- 미리보기와 실제 PDF의 차이를 확인할 수 있음


============================================================
[7. STEP 5 — 사용자 레퍼런스 기반 스타일 적용]
============================================================

목적:
사용자가 제공한 레퍼런스의 분위기를 분석하여
현재 문서에 적용한다.

사용 흐름:
레퍼런스 입력
→ 스타일 분석
→ 분석 결과 확인 및 수정
→ 현재 문서에 적용
→ 미리보기와 PDF 출력

입력 지원 순서:
1. 이미지 업로드
2. 레퍼런스 PDF의 선택 페이지
3. 접근 가능한 일부 URL

처음부터 모든 입력 형식을 한 번에 지원하지 않는다.

분석 대상:
- 주요 색상
- 제목과 본문의 크기 비율
- 여백 및 정보 밀도
- 정렬과 섹션 구분 방식
- 이미지 배치 특징
- 전체적인 분위기

추가 기능:
- 분석 결과를 사람이 읽을 수 있게 표시
- 분석된 설정을 사용자가 수정
- 지원하지 않는 특징은 대체 스타일 제안
- 적용 취소 및 기존 스타일 복원
- 레퍼런스와 생성 스타일 저장

구현 방향:
- STEP 4의 스타일 스키마로 분석 결과 변환
- 모델이 임의의 실행 코드나 HTML을 생성해서 적용하지 않음
- 생성된 스타일 값은 허용 범위 검사
- 폰트가 정확히 식별되지 않으면 유사한 분류로 대체
- 문서 내용 수정과 스타일 적용은 분리

AI 사용:
- 로컬 모델 또는 외부 API를 선택할 수 있음
- 외부 API는 전송 대상과 비용을 명시
- 스타일 분석에 불필요한 본문은 외부 전송하지 않음
- 레퍼런스 이미지 자체에도 민감정보가 있을 수 있음을 고려

URL 처리:
- 로그인·유료벽·접근 제한을 우회하지 않음
- 안전하지 않은 URL과 파일 접근 차단
- 허용 형식, 크기, 요청 시간 제한
- 지원하지 않는 사이트는 이미지 업로드 대안 제공

저작권:
레퍼런스는 스타일 참고 자료다.
이미지·로고·폰트 파일을 자동으로 가져와
재배포할 권리가 생기는 것은 아니다.

제외:
- 인터넷 자동 검색
- 모든 레퍼런스의 픽셀 단위 복제
- 기존 문서에 없는 사실이나 문장 생성

완료 기준:
- 여러 성격의 레퍼런스로 테스트
- 분석 결과를 수정 후 적용 가능
- 지원 불가능한 디자인 특징을 설명
- 원문 유지
- 실패 시 기존 문서와 스타일 보존


============================================================
[8. STEP 6 — 인터넷 레퍼런스 탐색 연동]
============================================================

목적:
앱 안에서 레퍼런스를 찾고,
선택한 레퍼런스를 STEP 5 분석 기능으로 연결한다.

사용 흐름:
검색어 입력
→ 결과 탐색
→ 레퍼런스 선택
→ 스타일 분석
→ 적용 및 저장

추가 기능:
- 검색 API 또는 허용된 자료 제공처 연결
- 썸네일 및 원본 링크 표시
- 검색 필터
- 즐겨찾기와 컬렉션
- 중복 결과 처리
- 검색 실패 및 호출 한도 안내
- 레퍼런스 출처 기록

구현 순서:
- 검색 제공처 1개부터 연결
- 단일 레퍼런스 선택부터 완성
- 이후 복수 레퍼런스 조합 추가

복수 레퍼런스 예:
- A에서 색상
- B에서 제목 스타일
- C에서 여백과 정보 밀도

충돌하는 설정에는 우선순위를 명시한다.

주의:
- 검색 결과에 있다는 이유로 재사용 가능한 것은 아님
- 출처와 확인 가능한 라이선스 정보를 표시
- 웹사이트의 약관과 수집 제한 준수
- 검색 API 비용과 제한 고려
- 네트워크 장애가 로컬 편집 기능까지 막지 않게 설계
- API 키를 프론트엔드 번들에 노출하지 않음

제외:
- 인터넷 전체 무제한 수집
- 로그인·유료벽 우회
- 검색 결과의 저작권 자동 보장

완료 기준:
- 검색부터 스타일 적용까지 앱 안에서 연결
- 결과의 원본 출처 확인 가능
- 검색 실패와 호출 한도를 정상 처리
- 검색 기능 없이도 기존 문서 편집 및 출력 가능


============================================================
[9. STEP 7 — 통합 PDF 리디자인 앱 안정화]
============================================================

목적:
앞 단계 기능을 통합하고,
지원 문서 범위를 넓히며 안정적으로 사용할 수 있게 한다.

이 단계는 큰 작업 묶음이다.
실제 구현 시 반드시 하위 단계로 나눈다.

권장 하위 단계:
7A. OCR 및 스캔 문서
7B. 표·다단 문서 지원 확대
7C. 검증과 부분 수정
7D. 설치형 패키징 및 배포 테스트

7A. OCR:
- 스캔 PDF 감지
- OCR로 글자와 위치 추출
- 한국어 인식 테스트
- 원본 이미지와 인식 결과 비교
- 불확실한 인식 결과 표시 및 수정
- 숫자와 기호 오류에 특히 주의

7B. 복잡한 문서:
- 기본 표 구조 추출과 편집
- 표의 페이지 나눔 처리
- 다단 문서 읽기 순서 처리
- 캡션과 이미지 연결
- 지원 불가능한 요소는 경고 또는 명시적 대안 제공

7C. 검증과 수정:
- 추출 및 변환 과정의 누락 후보 표시
- 출력에서의 넘침·잘림 점검
- 숫자·표 데이터 등 중요 항목 비교 보조
- 원본과 결과 대조
- 문제 위치로 이동
- 블록 단위 수정
- 취소 및 복구
- 긴 작업의 진행률·취소·오류 복구

검증 한계:
검사 기능이 있어도 내용 보존을 완벽하게 증명하는 것은 아니다.
불확실한 항목은 사용자 검토가 필요하다고 표시한다.

7D. 설치형 앱:
- Electron 또는 Tauri 검토
- 우선 지원 OS를 하나 정함
- 로컬 처리 엔진과 필요한 런타임 배포 방식 결정
- 폰트 사용 및 포함 방식 검토
- 사용자 데이터 저장 위치 명확화
- 백업과 복구
- 설치·업데이트·제거 테스트

PDF 출력:
STEP 1의 브라우저 인쇄 방식을 유지할지,
직접 파일 저장 방식으로 확장할지 판단한다.
직접 저장 기능이 필요하면 그에 맞는 출력 엔진을 선정한다.

성능:
- 파일 크기 및 페이지 수 한도
- 대용량 문서 메모리 관리
- 작업 중 앱 응답성 유지
- 악성 또는 손상된 문서 처리

완료 기준:
- 지원 PDF 유형을 명확히 문서화
- 지원 범위별 테스트 문서 세트 확보
- 개발자 PC 외 다른 PC에서도 실행
- 실패 시 원본과 작업 데이터 보호
- 문서 입력부터 출력까지 전체 흐름 검증
- 외부 AI·검색이 꺼져도 로컬 핵심 기능 사용 가능
- 알려진 제한사항과 수동 확인 항목 제공

최종 제품의 약속:
"지원 범위의 문서를 자동으로 재디자인하고,
불확실한 부분은 확인·수정할 수 있는 도구"

약속하지 않을 것:
"어떤 PDF든 완벽하게, 검수 없이 자동 변환"


============================================================
[10. 상품화는 별도 판단]
============================================================

7단계 구현 완료와 판매 준비 완료는 다르다.

판매 전에 확인할 항목:
- 실제 고객 수요
- 지원하는 문서 유형
- 알려진 제한사항
- 설치 및 사용 설명
- 상업용 라이선스
- 개인정보 처리와 외부 전송 안내
- 외부 API 비용 부담 주체
- 오류 대응 및 유지보수 범위
- 업데이트 정책
- 환불 및 판매 플랫폼 정책
- 다른 사용자 환경에서의 테스트

작은 범위로도 상품화할 수 있다.
예:
"교육일지 전용 PDF 제작기"
"보고서 디자인 변환 서비스"

기능을 전부 만든 후에야 수요를 확인하는 방식은 피한다.


============================================================
[11. 다른 AI가 단계별 구현 프롬프트를 만드는 방법]
============================================================

사용자가 "STEP N 프롬프트를 만들어줘"라고 하면:

1. 이 문서 전체 목표와 STEP N 범위를 읽는다.
2. 아래 진행 기록과 현재 코드를 확인한다.
3. 이전 단계가 완료됐다고 무조건 가정하지 않는다.
4. 현재 단계에 필요한 선행 기능만 점검한다.
5. 단계 범위가 크면 하위 작업으로 나눈다.
6. 다음 항목을 포함한 실행용 프롬프트를 작성한다.

프롬프트 필수 구성:
- 이번 단계 목표
- 기존 프로젝트 현황
- 사용자 흐름
- 구현할 기능
- 데이터 모델 변경
- 이전 저장 데이터 호환 처리
- 화면 구성
- 모듈 분리
- 오류 처리
- 개인정보·라이선스 고려
- 이번에 만들지 않을 기능
- 완료 기준
- 자동 및 수동 테스트
- 실행 명령
- 최종 보고 항목

프롬프트 작성 원칙:
- 기존 프로젝트를 이유 없이 새로 만들게 하지 않는다.
- 사용자 파일을 임의로 삭제하지 않게 한다.
- 라이브러리와 API 기능을 확인 없이 있다고 가정하지 않는다.
- 미확정 사항은 기본값 제안 또는 중요한 질문으로 분리한다.
- 정확한 작업시간이나 완벽한 변환을 보장하지 않는다.
- 이미 구현된 기능이 깨지지 않도록 회귀 테스트를 포함한다.
- 계획만 작성하고 끝내지 말고 실제 구현하도록 지시한다.
- 테스트 미실행 항목은 명확하게 표시하게 한다.
