너는 기존 프로젝트를 이어서 개발하는 시니어 프론트엔드 개발자다.

이번 작업은 “로컬 문서 디자인 / PDF 리디자인 앱”의
STEP 2 — 개인 문서 제작기 구현이다.

계획이나 예시 코드만 제시하고 끝내지 말고,
현재 프로젝트를 조사한 뒤 실제 파일을 수정하고 가능한 테스트를 실행하라.

============================================================
1. 이번 단계의 목표
============================================================

기존의 회고록 고정 양식 앱을 확장하여,
학습일지와 간단한 보고서도 작성할 수 있는 개인 문서 제작기를 만든다.

최종 사용자 흐름:

새 문서 생성 또는 저장 문서 선택
→ 섹션 추가·수정·정렬
→ 본문 작성 및 이미지 추가
→ 디자인 선택
→ 로컬 자동 저장
→ 프로젝트 파일 백업 또는 브라우저 인쇄로 PDF 저장

이번 단계에서는 자유로운 캔버스 편집기가 아니라,
순서가 있는 섹션과 블록을 편집하는 문서 제작기를 구현한다.

STEP 3 이후의 PDF 분석, AI, 인터넷 검색 등은 구현하지 않는다.

============================================================
2. 기존 프로젝트 확인
============================================================

사용자는 STEP 1을 완료했다고 알렸다.
다만 인수인계 문서의 진행 기록은 갱신되지 않았을 수 있다.

먼저 다음 항목을 실제 코드에서 확인하라.

- 프로젝트 구조와 package.json
- 사용 기술 및 설치된 의존성
- 실제 개발·빌드·테스트 명령
- STEP 1 문서 타입과 디자인 타입
- localStorage 키 및 저장 데이터 구조
- schemaVersion 처리
- 자동 저장과 복원 로직
- 공통 문서 렌더러
- 화면 및 인쇄 CSS
- 기존 테마 3종
- 예시 불러오기와 초기화 동작
- 기존 테스트 및 알려진 문제

중요 원칙:

- 프로젝트를 이유 없이 새로 생성하지 않는다.
- 기존 파일과 사용자 데이터를 임의로 삭제하지 않는다.
- 관련 없는 리팩터링은 하지 않는다.
- 기존 라이브러리로 충분하면 우선 재사용한다.
- 라이브러리 API는 실제 설치 버전과 문서 또는 타입을 확인한다.
- 사용자 문서 본문이나 이미지 데이터를 로그에 출력하지 않는다.
- STEP 1의 부족한 부분이 있다면 STEP 2에 필요한 선행 문제만 수정한다.

시작 시 확인한 현황과 간단한 작업 순서를 설명한 후 구현을 진행하라.
작업을 막지 않는 미확정 사항은 아래 기본값으로 결정하고 보고하라.
프로젝트 위치나 데이터 호환성처럼 안전한 판단이 불가능한 경우에만 질문하라.

============================================================
4. 구현할 기능
============================================================

4-1. 여러 문서 관리

다음을 구현한다.

- 문서 목록
- 새 문서 생성
- 저장 문서 열기
- 문서 이름 변경
- 문서 복제
- 문서 삭제
- 수정일 표시
- 마지막으로 열었던 문서 복원

문서 목록 이름과 실제 출력되는 문서 제목은 구분한다.

- 문서 이름: 목록과 백업 파일 관리용
- 문서 제목: 실제 문서에 출력되는 제목

문서 이름을 바꿔도 출력 제목은 임의로 변경하지 않는다.

새 문서 생성 방식은 최소 다음 두 가지를 제공한다.

1. 빈 문서
2. 기존 회고록 양식

기존 회고록 예시는 새 예시 문서로 생성하는 방식을 우선한다.
기존 문서를 조용히 덮어쓰지 않는다.

기존 “초기화”가 남아 있다면 “현재 문서 초기화”처럼 범위를 명시한다.
전체 저장 문서를 지우는 기능으로 확대하지 않는다.

문서 삭제는 확인 후 수행하고, 다른 문서나 다른 문서의 이미지는 손상시키지 않는다.

4-2. 섹션 편집

다음을 구현한다.

- 섹션 추가
- 섹션 제목 수정
- 섹션 삭제
- 섹션 위/아래 이동
- 섹션 내부 본문 편집
- 섹션 내부 블록 추가·삭제·위/아래 이동

드래그 앤 드롭은 필수가 아니다.
위/아래 버튼으로 모든 순서 변경이 가능하면 충분하다.

섹션 이동 시 그 섹션의 본문과 이미지가 함께 이동해야 한다.
섹션 삭제 시 삭제되는 범위를 확인할 수 있어야 한다.

본문은 일반 텍스트 기반으로 처리한다.
리치 텍스트 편집기나 Markdown 파서는 도입하지 않아도 된다.

사용자 텍스트를 임의로 요약·교정·재작성하지 않는다.
표시 여부 판단을 위한 공백 검사는 가능하지만 저장 원문은 변경하지 않는다.

4-3. 이미지

최소 지원 형식:

- PNG
- JPEG
- WebP

SVG, GIF 및 그 외 형식은 이번 단계에서 지원하지 않아도 된다.
지원하지 않는 파일은 이유를 안내하고 거절한다.

다음을 구현한다.

- 로컬 이미지 파일 추가
- 이미지 미리보기
- 이미지 교체
- 이미지 삭제
- 이미지 설명 입력
- 왼쪽 / 가운데 / 오른쪽 정렬
- 작게 / 보통 / 크게 크기 선택
- 본문과 이미지의 순서 변경

이미지 설명은 캡션으로 출력한다.
별도 대체 텍스트 입력이 없다면 설명을 대체 텍스트에도 활용하되,
화면낭독기에서 불필요한 중복 낭독이 발생하지 않도록 고려한다.

크기 기본값 예:

- 작게: 문서 콘텐츠 폭의 35%
- 보통: 65%
- 크게: 100%

이미지의 원래 종횡비는 유지한다.
자르기, 늘이기, 임의의 내용 변경은 하지 않는다.

기본 제한 제안:

- 이미지 1개당 10MiB
- 이미지 1개당 2,000만 픽셀
- 프로젝트 가져오기 파일 100MiB

제한값은 한곳에서 관리하고 UI에 안내한다.
기술적 이유로 변경하면 근거를 기록한다.

확장자와 MIME만 믿지 말고 실제 이미지 디코딩 가능 여부도 확인한다.
가능한 경우 크기 정보 확인 후 큰 이미지의 디코딩을 제한한다.
클라이언트 측 검사만으로 모든 악성 파일을 차단한다고 주장하지 않는다.

자동 압축이나 리사이즈로 원본을 조용히 변경하지 않는다.
처리할 수 없는 이미지는 기존 문서를 유지한 채 오류를 안내한다.

5. 데이터 모델
============================================================

실제 STEP 1 타입을 확인한 후 schemaVersion: 2로 확장한다.
내용과 디자인은 별도 필드로 유지한다.

과도한 범용 문서 모델은 만들지 않는다.

권장 구조:

DocumentV2
- schemaVersion: 2
- id
- name
- createdAt
- updatedAt
- content
  - title
  - author
  - date
  - sections[]
- design

Section
- id
- title
- blocks[]

Block
- HeadingBlock
- ParagraphBlock
- ImageBlock

HeadingBlock
- id
- type: "heading"
- text

ParagraphBlock
- id
- type: "paragraph"
- text

ImageBlock
- id
- type: "image"
- assetId
- caption
- alignment: "left" | "center" | "right"
- size: "small" | "medium" | "large"

섹션 제목은 섹션 메타데이터로 관리하고,
HeadingBlock은 섹션 내부 소제목이 필요한 경우 사용한다.
UI에서는 “소제목 / 본문 / 이미지” 추가 정도로 단순하게 제공한다.

별도 이미지 자산:

ImageAsset
- id
- documentId
- mimeType
- originalName
- byteSize
- width
- height
- blob

모든 섹션과 블록은 안정적인 ID를 가진다.
배열 인덱스를 영속 ID나 React key 대신 사용하지 않는다.

문서 수정 시 updatedAt을 갱신한다.
날짜의 기본값은 STEP 1처럼 로컬 기준 오늘을 사용한다.

빈 섹션 출력 규칙:

- 소제목만 있고 본문·이미지가 없는 섹션은 출력에서 숨긴다.
- 비어 있지 않은 본문 또는 이미지가 있으면 출력한다.
- 섹션 제목이 비어 있어도 본문·이미지는 출력한다.
- 편집 화면에서는 빈 섹션도 계속 편집할 수 있어야 한다.

============================================================
6. 로컬 저장과 데이터 보호
============================================================

문서와 이미지는 IndexedDB에 저장한다.

권장 저장 단위:

- documents
- assets
- appSettings 또는 migration metadata

네이티브 IndexedDB 또는 작은 래퍼 라이브러리 중
현재 프로젝트에 적합한 방식을 선택한다.

이미지 Blob이나 대용량 Base64 문자열을 localStorage에 저장하지 않는다.
localStorage는 필요하면 작은 설정값이나 기존 데이터 읽기에만 사용한다.

자동 저장:

- 짧은 debounce 적용
- “저장 중 / 저장됨 / 저장 실패” 상태 표시
- 문서 전환 시 현재 문서 저장 완료를 확인
- 이전 문서의 지연 저장이 다음 문서에 적용되지 않게 처리
- 비동기 저장 순서 때문에 최신 변경이 오래된 값으로 덮이지 않게 처리
- 초기 로딩 전에 빈 기본값을 자동 저장하지 않음

저장 실패 시:

- 현재 편집 내용을 메모리에 유지
- 오류와 재시도 방법 안내
- 성공하지 않았는데 “저장됨” 표시 금지
- 저장되지 않은 내용이 있는 상태에서 페이지 이탈 시 경고
- 현재 편집 상태를 프로젝트 파일로 내보낼 수 있는 복구 경로 제공

beforeunload만으로 비동기 저장을 보장한다고 가정하지 않는다.

문서·이미지 변경은 가능한 범위에서 트랜잭션으로 처리한다.
교체 이미지 저장에 실패했다고 기존 이미지부터 삭제하지 않는다.

복제는 새 문서·섹션·블록·이미지 ID를 발급하고 참조를 다시 연결한다.
이번 단계에서는 독립 이미지 복사 방식으로 단순하게 구현해도 된다.
원본 삭제가 복제 문서에 영향을 주면 안 된다.

문서 삭제 시 해당 문서 전용 이미지도 정리한다.
공유 자산 설계를 선택한다면 실제 참조 여부를 확인한 후 삭제한다.

여러 탭 동시 편집을 지원하지 않는다면 그 제한을 안내하고,
가능한 범위에서 충돌 감지 또는 두 번째 탭의 편집 제한을 제공한다.
실시간 협업 시스템으로 확대하지 않는다.

============================================================
7. STEP 1 저장 데이터 마이그레이션
============================================================

STEP 1의 실제 localStorage 키와 타입을 확인해 변환기를 작성한다.
가상의 키나 필드명을 기존 구조라고 가정하지 않는다.

변환 규칙:

- 기존 제목·작성자·작성일 유지
- 기존 네 개 본문 항목을 해당 제목의 섹션으로 변환
- 각 본문은 원문을 보존한 ParagraphBlock으로 변환
- 기존 테마·색상·폰트·본문 크기 유지
- 줄바꿈, 공백, 숫자 및 특수문자 보존
- 빈 항목도 편집 가능한 섹션으로 유지 가능
- 출력 시에는 빈 섹션 숨김 규칙 적용

안전 조건:

- STEP 2 문서와 마이그레이션 완료 표시는 같은 트랜잭션으로 기록
- 저장 성공 전에는 완료 표시를 남기지 않음
- 재실행해도 같은 회고록이 중복 생성되지 않음
- 기존 localStorage 원본은 자동 삭제하지 않음
- 기존 데이터가 손상되었으면 원본을 유지하고 사용자에게 안내
- 마이그레이션 실패를 이유로 기존 데이터를 초기화하지 않음
- 알 수 없는 미래 schemaVersion을 임의로 변환하지 않음

IndexedDB 자체 버전과 문서 schemaVersion은 별개로 관리한다.

============================================================
8. 프로젝트 파일 내보내기·가져오기
============================================================

현재 문서 하나를 이미지까지 포함하여 내보내고,
다른 브라우저나 PC에서도 가져올 수 있게 한다.

이번 단계의 기본 형식:

- JSON 기반 단일 프로젝트 파일
- format 식별자
- formatVersion
- document
- assets[]
- 이미지 데이터는 Base64로 포함

확장자 예: .localdoc.json

실제 확장자는 프로젝트에 맞게 정하되 README에 명시한다.
로컬 파일 경로, Blob URL, IndexedDB 키만 내보내지 않는다.
이미지 실데이터가 파일에 포함되어야 한다.

내보내기:

- 현재 메모리의 최신 편집 내용 기준
- 참조하는 이미지를 빠짐없이 포함
- 누락된 이미지가 있으면 완전한 백업이라고 표시하지 않음
- 파일 이름에는 안전하게 정리한 문서 이름 사용
- 임시 Object URL은 적절한 시점에 해제

가져오기:

- 파싱 전에 파일 크기 검사
- format 및 버전 검사
- 필수 필드·타입·문자열 길이·배열 개수 검사
- 테마, 색상, 정렬, 크기 등의 허용값 검사
- 중복 ID, 누락 자산, 잘못된 자산 참조 검사
- Base64 형식·디코딩 크기·이미지 디코딩 가능 여부 검사
- 블록 수와 전체 이미지 용량 제한
- 객체를 무작정 병합하지 않고 검증한 필드로 새 객체 구성

가져온 문서는 기본적으로 새 문서로 추가한다.
문서·섹션·블록·자산 ID를 재발급하고 참조를 갱신한다.
기존 문서를 덮어쓰지 않는다.

전체 검증 후 트랜잭션으로 저장한다.
검증이나 저장 실패 시 일부 문서·이미지만 남기지 않는다.

지원하지 않는 미래 버전은 이유를 안내하고 거절한다.
HTML, JavaScript, 임의 CSS나 외부 URL을 실행·적용하지 않는다.

전체 문서함 백업과 ZIP 압축은 이번 단계의 필수 범위가 아니다.

9. 화면 구성
============================================================

기존 UI를 최대한 재사용하면서 다음 영역을 제공한다.

A. 문서 목록
- 새 문서
- 문서 선택
- 이름 변경
- 복제
- 삭제

B. 현재 문서 편집
- 관리용 이름
- 출력 제목
- 작성자
- 작성일
- 섹션 편집
- 소제목·본문·이미지 블록 편집

C. 디자인 설정
- 기존 설정 유지
- 추가 테마

D. 공통 문서 미리보기

E. 문서 작업
- 저장 상태 및 재시도
- 프로젝트 내보내기
- 프로젝트 가져오기
- PDF 인쇄

데스크톱에서 문서 목록 때문에 미리보기가 지나치게 좁아지지 않게 한다.
목록은 접이식 패널이나 서랍 형태여도 된다.
작은 화면은 세로 배치 또는 탭 전환을 사용할 수 있다.

접근성:

- 입력 요소 label
- 키보드로 조작 가능한 버튼
- 첫 번째·마지막 항목의 이동 버튼 비활성화
- 삭제·이동 버튼의 대상을 알 수 있는 이름
- 오류를 색상만으로 표시하지 않음
- 저장 상태를 과도하게 반복 낭독하지 않음

10. 테마와 PDF 출력
============================================================

기존 3개 테마를 새 블록 구조에서도 유지한다.

추가로 최소 1개 테마를 구현한다.
예: “컴팩트 리포트”

색상만 바꾼 테마가 아니라 다음 중 여러 요소를 구분한다.

- 제목 배치
- 섹션 라벨
- 구분선
- 여백
- 캡션 표현

추가 테마도 기존 고딕·명조 및 크기 설정과 호환되어야 한다.
STEP 4의 디자인 조합 엔진은 미리 만들지 않는다.

화면과 인쇄는 같은 문서 렌더러와 디자인 규칙을 사용한다.

이미지 인쇄:

- 콘텐츠 폭 초과 방지
- 종횡비 유지
- 한 페이지의 인쇄 가능 높이 안으로 축소
- 이미지와 짧은 캡션은 가능한 한 함께 출력
- 긴 캡션 때문에 figure 전체가 잘리지 않도록 별도 처리
- 긴 섹션 전체를 break-inside: avoid로 묶지 않음
- overflow: hidden 등으로 내용을 숨겨 문제를 덮지 않음

이미지 로딩·디코딩과 필요한 렌더링이 완료되기 전에
인쇄를 시작해 이미지가 빠지는 상황을 방지한다.
이미지 로딩 실패 시 조용히 누락하지 말고 안내한다.

다음은 실제 브라우저에서 확인해야 한다.

- 가로·세로 이미지
- 큰 이미지
- 긴 캡션
- 여러 페이지 문서
- 섹션 경계 주변의 이미지

브라우저 인쇄 특성상 완전히 동일한 페이지 배치를 보장하지 않는다.

12. 개인정보·보안·라이선스
============================================================

- 백엔드, 외부 API, CDN을 추가하지 않는다.
- 개발 서버는 localhost에만 바인딩한다.
- 문서와 이미지를 외부로 전송하지 않는다.
- 텍스트를 dangerouslySetInnerHTML 등으로 렌더링하지 않는다.
- 가져온 문서의 URL로 외부 자산을 자동 다운로드하지 않는다.
- 문서 내용이나 이미지 Base64를 로그에 남기지 않는다.
- 새 의존성은 버전·목적·라이선스를 기록한다.
- 외부 폰트나 이미지를 임의로 포함하지 않는다.
- 시스템 폰트를 유지한다.

사용자 안내:

- 데이터는 현재 브라우저 프로필과 앱 origin에 저장됨
- 브라우저 데이터 삭제 또는 origin 변경 시 접근하지 못할 수 있음
- 정기적인 프로젝트 파일 백업 권장
- 내보낸 프로젝트 파일은 암호화되지 않음
- 이미지 메타데이터가 원본에 포함되어 있을 수 있음
- 시크릿 모드나 저장 공간 부족으로 저장이 제한될 수 있음

로컬 저장을 영구 보존이나 자동 백업이라고 표현하지 않는다.

15. 자동 테스트
============================================================

기존 테스트 도구를 우선 사용한다.
없다면 필요한 범위에 맞는 최소 도구를 도입하고 이유를 기록한다.

핵심 테스트:

데이터와 편집
- 섹션·블록 추가, 삭제, 이동
- 첫 항목·마지막 항목 이동 경계
- 제목·본문·이미지 순서 유지
- 테마 변경 전후 내용 동일
- 빈 섹션 출력 규칙
- 복제 문서의 ID 독립성과 자산 참조

마이그레이션
- 정상 STEP 1 데이터 변환
- 줄바꿈·공백·특수문자 보존
- 기존 디자인 유지
- 재실행 시 중복 생성 방지
- 저장 실패 시 완료 표시와 원본 삭제 없음
- 손상된 데이터와 알 수 없는 버전 처리

저장
- 문서와 이미지 저장 후 복원
- 문서 전환 중 지연 저장의 문서 혼동 방지
- 빠른 수정 시 최신 내용 유지
- 저장 실패 시 편집 상태 보존
- 원본 삭제 후 복제 문서 정상 유지

프로젝트 파일
- 텍스트·이미지·디자인 왕복 복원
- 새 ID와 이미지 참조 연결
- 잘못된 JSON
- 지원하지 않는 버전
- 잘못된 설정값
- 중복 ID
- 누락된 이미지
- 손상된 Base64·이미지
- 크기·개수 제한 초과
- 실패 시 부분 데이터 미생성

이미지
- 지원 형식 허용
- 미지원 형식 거절
- 크기 제한
- 손상된 이미지 거절

브라우저 API를 모킹한 테스트와 실제 브라우저 검증을 구분한다.
모킹 테스트 통과를 실제 IndexedDB·PDF 검증 성공으로 보고하지 않는다.

16. 수동 테스트
============================================================

Chrome/Edge 우선으로 다음을 점검한다.

1. 기존 STEP 1 저장 데이터가 있는 환경에서 실행
2. 기존 회고록의 내용과 디자인 유지 확인
3. 빈 문서와 회고록 양식 생성
4. 섹션 추가·삭제·이름 변경·순서 변경
5. 본문·소제목·이미지 블록 순서 변경
6. 가로·세로·큰 이미지 추가
7. 설명·정렬·크기 조절
8. 새로고침 후 내용·이미지·디자인 복원
9. 두 문서를 빠르게 전환해 데이터 섞임 여부 확인
10. 이미지 포함 문서 복제 후 원본 삭제
11. 프로젝트 내보내기
12. 별도 브라우저 프로필 또는 다른 origin에서 가져오기
13. 잘못된 프로젝트 파일 가져오기 시 기존 문서 보존
14. 여러 페이지 문서를 PDF로 저장
15. PDF에 앱 UI가 없는지 확인
16. 한글 정상 출력 및 텍스트 선택 확인
17. 이미지 잘림·왜곡·누락 확인
18. 긴 본문·긴 URL·긴 캡션의 누락 여부 확인
19. 기존 테마 3종과 추가 테마 확인
20. 작은 화면·키보드 조작 확인
21. 백엔드나 외부 API 없이 핵심 기능 동작 확인

실제 사용자 문서를 마음대로 수정하거나 삭제하며 테스트하지 않는다.
테스트용 문서와 별도 저장 환경을 사용한다.
